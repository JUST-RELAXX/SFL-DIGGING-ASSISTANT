# skills.md — styling pass context (read this fully before writing any CSS)

## What you're styling

SFL Game Assistant is a Manifest V3 Chrome extension for the game Sunflower Land. A previous agent pass (Claude) built four new data panels — a stats bar (Alt+2), a hints/legend panel (Alt+3), a today's-formations panel (Alt+4), and a treasure-economics panel (Alt+5) — plus an Alt+E shortcut that shows all four. They are functionally correct: real data, real calculations, wired to real hotkeys. They currently look like plain unstyled boxes. Your job is exclusively visual: positioning/anchoring, the formation-shape rendering, and a glass-style visual redesign. Do not change any data logic, calculations, or hotkey behavior. Do not restyle the grid overlay itself (`#sfl-grid-wrapper`, `#sfl-master-grid`) — it already has its own design language and is out of scope here; only the four new panels get the redesign.

Before writing any code, inspect the current DOM and CSS yourself to find the actual element ids/classes the previous pass used for these four panels — this document doesn't guess at exact selectors, confirm them against the live code first.

## 1. The anchoring problem

The grid overlay already has a working "attached and stabilized" positioning system: `#sfl-grid-wrapper` is `position: fixed`, has a locked mode (`.sfl-mode-locked`, pointer-events disabled, click-through to the game) and an unlocked/drag mode (`.sfl-mode-unlocked`, draggable, `cursor: grab`), and its position persists via `chrome.storage`. The four new panels right now are not part of this system — they float independently and don't move or lock together with the grid.

Fix this: the new panels need to be positioned relative to `#sfl-grid-wrapper`'s own coordinates (as children of it, or as siblings whose position is recalculated whenever the wrapper moves/is dragged/is loaded from storage), so that wherever the player drags the grid, the stats bar stays glued above it, the hints and formations panels stay glued beside it, and the treasure-stat panel stays glued wherever its own reference position is. Reuse the existing lock/unlock and storage-persistence mechanism rather than inventing a second one — read how `#sfl-grid-wrapper`'s position is saved and restored, and hook the same lifecycle for these panels' offsets relative to it.

## 2. Reference layout for panel placement

The user has supplied annotated screenshots (see the prompt for which image numbers to use) showing where each panel belongs relative to the grid: stats bar directly above the grid, hints panel to the right of the grid, formations ("Today's formations") panel below or continuing from the hints panel on the right side, treasure-stat panel positioned near where indicated in the reference. Match relative placement and rough proportions from these images — don't invent a different layout.

## 3. Formation shapes are currently wrong — they need to be real mini-grids, not colored boxes

Right now "Today's formations" renders each formation as a flat colored square next to a text label. That's a placeholder that was never meant to be final. It needs to become an actual small grid showing the formation's real shape: a compact grid (the old extension used a 4-wide layout) where most cells are empty/transparent and only the cells that are part of that formation's footprint show the actual item icon in its correct relative position. This is a pure rendering change — the position data already exists in the codebase (the `DIGGING_FORMATIONS` table already ported into `digging-solver.js` gives you each formation's list of `{x, y, name}` relative plot positions), and the actual icon image files already exist in the extension's own `ITEMS/` folder (already declared in `manifest.json`'s `web_accessible_resources`, already used elsewhere in the codebase) — filenames like `camel_bone.webp`, `old_bottle.png`, `hieroglyph.webp`, `vase.webp`, `seaweed.webp`, `wooden_compass.webp`, `otter_pebble.webp`, `sea_cucumber.webp`, `clam_shell.webp`, `cockle_shell.webp`, `coral.png`, `pearl.webp`, `pipi.webp`, `starfish.png`, `stone.png`, `wood.png`, `sand.webp`, `crab.png`, `salt_dino_egg.webp`. Map each formation's item name to its matching file in that folder and render it at the right cell.

One more detail from the reference screenshots, worth replicating if it's feasible without new game-data work: cells belonging to the "Coprolite" item specifically get a distinct visual treatment in the old extension — an orange/gold glow with a diagonal highlight across the icon, visually separate from the plain green-bordered highlight used for every other formation cell. This is because Coprolite has its own separate streak-tracking mechanic in the game (find three to unlock a bonus). Give Coprolite cells that same distinct treatment if the formation data lets you identify them by item name; if it doesn't cleanly identify them, skip this detail rather than guessing — the plain green-highlighted rendering for every cell is still a massive improvement over flat colored boxes and is an acceptable fallback.

## 4. The liquid-glass visual language

The user wants Apple-style "Liquid Glass" glassmorphism applied to these four panels, referencing `github.com/rdev/liquid-glass-react` as the look to aim for. That specific project is a React component and this extension has no React and no bundler — it's plain script tags loaded by a Manifest V3 content script — so don't try to npm-install it or add a build pipeline just for this. Instead, replicate its actual visual technique directly in CSS, which works fine in a plain content script since none of the underlying technique is React-specific:

- **Base frosted-glass layer**: `backdrop-filter: blur(Npx) saturate(N%)` on the panel itself, combined with a semi-transparent light background fill (roughly `rgba(255, 255, 255, 0.08–0.15)` depending on what sits behind it) and a large `border-radius`.
- **Specular edge highlight**: this is what actually sells the "glass" look and is easy to get wrong by skipping it. Layer inset box-shadows to simulate a thin bright edge catching light plus outer depth, roughly in the shape of: a hairline near-white inset shadow at very low spread (the "glass edge"), a slightly larger soft inset highlight, and a soft outer drop shadow for lift off the background. The reference project's own values are close to `box-shadow: 0 0 0 0.5px rgba(255,255,255,0.5) inset, 0 1px 3px rgba(255,255,255,0.25) inset, 0 1px 4px rgba(0,0,0,0.35), 0px 12px 40px rgba(0,0,0,0.25)` — treat these as a starting point to tune, not gospel.
- **Optional stretch goal, only after the above looks good**: the reference project's true refraction/chromatic-aberration effect comes from an SVG `<filter>` using `feImage` (a displacement map) feeding into `feDisplacementMap`, applied three times at slightly different scales per RGB channel for the chromatic-aberration edge fringe, then a `feGaussianBlur` pass, applied to the element via `filter: url(#yourFilterId)` alongside the `backdrop-filter`. SVG filters are plain DOM/markup, not React — you can inject one into `content.js` the same way the grid overlay's own DOM is built. This is a genuine visual upgrade over the base recipe above, but it's meaningfully more work and lower priority than getting the base frosted-glass look, the anchoring fix, and the formation shapes solid first.
- Known limitation to inherit from the reference project: this kind of SVG-filter-driven displacement doesn't render in Firefox/Safari the same way it does in Chromium — since this extension is Chrome-only that's not a real constraint here, but keep the base `backdrop-filter` recipe as a working fallback regardless.

Apply this treatment to all four new panels consistently — same corner radius, same blur/saturation, same highlight treatment — so they read as one coherent design system, not four different experiments.

## 5. What "done" looks like

Each of the four panels sits glued to the grid overlay and moves/locks with it exactly like the grid does; the formations panel shows real per-formation shapes with real item icons instead of flat squares; all four panels share one consistent frosted-glass visual treatment; the grid overlay itself is visually untouched.
